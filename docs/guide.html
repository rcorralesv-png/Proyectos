Hello Secure World · Guía de Práctica

Práctica Real en GitHub — DevSecOps con GitHub Actions

Tiempo estimado: 60–90 minutos Nivel: Intermedio 3 escenarios manos-a-la-obra
Al completar esta guía podrás:
  • Configurar un fork con los controles de seguridad reales de GitHub
  • Ver un Security Gate de SCA bloquear un merge con una dependencia vulnerable
  • Experimentar GitHub Push Protection rechazando un push con un secreto
  • Interpretar una alerta de CodeQL con taint tracking y aplicar el fix
  • Verificar tus resultados con los códigos HSW-PRACTICE-*

Introducción

El simulador interactivo de Hello Secure World te mostró cómo funcionan los controles de seguridad de forma conceptual. Esta práctica te pone en el lugar del desarrollador: cometerás los errores reales, observarás los controles en acción y aprenderás a corregirlos.

Trabajarás en tu propio fork del repositorio. Cada escenario introduce un problema de seguridad deliberado y un ciclo completo de detectar → entender → corregir → verificar.

Prerequisitos

Antes de empezar necesitas:
  • Cuenta de GitHub — gratuita. Todos los controles de esta guía funcionan en repositorios públicos sin costo.
  • Git instalado en tu equipo (git-scm.com)
  • Node.js 18 o superior (nodejs.org)
  • Haber completado los 11 labs del simulador (recomendado, no obligatorio)
Módulo 1 de 4

Configuración del Fork

⏱ ~10 minutos 🔧 Configuración única
En este módulo configurarás:
  • Tu fork del repositorio con GitHub Actions habilitado
  • Secret Scanning con Push Protection activo
  • CodeQL Analysis para JavaScript/TypeScript
  • Branch Protection con Required Status Checks (recomendado)
Unidad 1.1

Fork y clon del repositorio

  1. En la página del repositorio original, haz clic en el botón Fork (esquina superior derecha).

  2. Selecciona tu cuenta de GitHub como destino del fork y confirma con Create fork.

  3. Clona tu fork localmente e instala las dependencias:

    # Reemplaza TU_USUARIO con tu nombre de GitHub
git clone https://github.com/TU_USUARIO/Hello_Secure_World.git
cd Hello_Secure_World
npm install

  4. Verifica que el proyecto funciona correctamente:

    npm test

    Deberías ver 33 passed en la salida.

Unidad 1.2

Habilitar GitHub Actions

  1. En tu fork, ve a la pestaña Actions.

  2. Si ves el mensaje "Workflows aren't being run on this forked repository", haz clic en I understand my workflows, go ahead and enable them.

Los tres workflows que estarán disponibles son:

  • CI — Calidad (ESLint), pruebas (Vitest) y seguridad (npm audit)
  • CodeQL Analysis — Análisis SAST de JavaScript/TypeScript
  • Lab Validation — Validación de los escenarios de práctica
Unidad 1.3

Secret Scanning y Push Protection

✅
Consejo En repositorios públicos Secret Scanning y Push Protection están habilitados por defecto. Solo sigue estos pasos si tu fork es privado.

  1. Ve a Settings → Security → Code security and analysis.

  2. En la sección Secret scanning, haz clic en Enable.

  3. En la sección Push protection, haz clic en Enable.

    ⚠️
    Importante Push Protection es el control que bloquea el push antes de que el secreto llegue al historial. Sin él, Secret Scanning solo detecta; no previene.
Unidad 1.4

CodeQL Analysis

CodeQL se activa automáticamente a través del workflow codeql.yml incluido en el repositorio. No requiere configuración adicional — el análisis se ejecuta en cada Pull Request.

Para verificar que está activo:

  1. Ve a Settings → Security → Code security and analysis.

  2. En la sección Code scanning, deberías ver CodeQL listado como herramienta activa.

Unidad 1.5

Branch Protection (recomendado)

Branch Protection convierte los controles automáticos en Security Gates reales: ningún PR puede mergearse si un required status check falla.

  1. Ve a Settings → Branches → Add branch protection rule.

  2. En Branch name pattern, escribe main.

  3. Activa las siguientes opciones:

    • ✅ Require status checks to pass before merging
    • ✅ Require branches to be up to date before merging

  4. En el buscador de status checks, agrega:

    • security / Verificar dependencias
    • CodeQL / Analyze (javascript-typescript)

  5. Haz clic en Create.

Unidad 1.6

Verificar la configuración

Crea un PR de prueba vacío para confirmar que todos los checks se ejecutan:

git checkout -b test/setup-verification
git commit --allow-empty -m "test: verificar configuración de CI"
git push origin test/setup-verification

Abre el PR en GitHub. Deberías ver los siguientes checks ejecutarse:

  • ✅ quality / Lint y formato
  • ✅ test / Pruebas unitarias
  • ✅ security / Verificar dependencias
  • ⏳ CodeQL / Analyze (javascript-typescript) — puede tardar 5–10 min

Cuando todos estén verdes, cierra el PR sin mergear y elimina la rama:

git checkout main
git push origin --delete test/setup-verification
git branch -D test/setup-verification
✅
Listo Tu fork está configurado. Continúa con cualquiera de los tres escenarios de práctica.
Comprueba tus conocimientos

¿Qué diferencia a Secret Scanning de Secret Scanning + Push Protection?

Secret Scanning solo detecta secretos ya en el historial (modo reactivo). Push Protection bloquea el push antes de que el secreto llegue al repositorio (modo preventivo). Ambos son complementarios, pero Push Protection es el control proactivo.

Módulo 2 de 4 · Escenario 01

SCA: Dependencia Vulnerable

⏱ ~15 minutos 🔒 Control: npm audit 🎯 CVE-2020-8203 · lodash
Al completar este escenario podrás:
  • Reproducir un fallo de SCA en CI con una dependencia HIGH
  • Leer el reporte de npm audit e identificar el CVE afectado
  • Aplicar el fix (actualizar la dependencia) y verificar que CI vuelve a pasar
  • Explicar por qué package-lock.json es crítico para SCA
Unidad 2.1

Contexto del problema

El archivo practice/scenarios/01-sca/package.json incluye lodash@4.17.4. Esta versión contiene CVE-2020-8203 (Prototype Pollution, severidad HIGH, CVSS 7.4).

El job security de CI ejecuta npm audit --audit-level=high con la política HIGH o CRITICAL → FAIL. Cuando el job falla, el status check del PR falla — y si tienes Branch Protection configurado, el merge queda bloqueado.

ℹ️
Scanner vs Security Gate npm audit es el scanner. La combinación de --audit-level=high + Required Status Check en Branch Protection es lo que lo convierte en un Security Gate: si falla el check, el merge no puede avanzar.
Unidad 2.2

Pasos del escenario

  1. Introduce la dependencia vulnerable en la raíz de tu fork clonado:

    cp practice/scenarios/01-sca/package.json package.json
npm install   # regenera package-lock.json con lodash@4.17.4

  2. Verifica localmente que npm audit detecta el problema:

    npm audit --audit-level=high

    Salida esperada:

    lodash  <4.17.21
Severity: high
Prototype Pollution — https://github.com/advisories/GHSA-jf85-cpcp-j695
fix available via `npm audit fix`
node_modules/lodash

1 high severity vulnerability

  3. Abre un Pull Request desde una rama nueva:

    git checkout -b lab/sca-vulnerable-dep
git add package.json package-lock.json
git commit -m "lab: introduce dependencia vulnerable para práctica SCA"
git push origin lab/sca-vulnerable-dep

    En GitHub, abre un Pull Request desde lab/sca-vulnerable-dep hacia main.

  4. Observa el fallo de CI en la pestaña Actions de tu fork:

    • ✅ quality — PASSED
    • ✅ test — PASSED
    • ❌ security / Verificar dependencias — FAILED

    El botón Merge estará deshabilitado si tienes Branch Protection configurado.

  5. Corrige la vulnerabilidad actualizando lodash:

    npm install lodash@^4.17.21
git add package.json package-lock.json
git commit -m "fix: actualizar lodash a versión segura (CVE-2020-8203)"
git push

  6. Verifica que CI pasa. El nuevo push dispara un nuevo run en CI. Observa en Actions cómo el job security ahora reporta ✅ PASSED.

🏆
Código de verificación Cuando todos los checks estén en verde, el workflow lab-validate.yml publicará automáticamente en el PR un comentario con tu código HSW-PRACTICE-01-XXXXXXXXXXXXXXXX. Guárdalo para compartir con tu instructor.
Unidad 2.3

Conceptos clave

Por qué importa package-lock.json

npm audit analiza el árbol de dependencias bloqueado por el lockfile, no solo el rango declarado en package.json. Si el lockfile resuelve lodash@4.17.4, npm audit detectará el CVE aunque en package.json el rango permita versiones más nuevas. Por eso ambos archivos deben estar en el repositorio.

Riesgo residual de SCA

SCA solo detecta vulnerabilidades documentadas con CVE. No puede detectar:

  • Zero-days (vulnerabilidades no conocidas públicamente)
  • Paquetes maliciosos sin CVE registrado (supply chain attacks)
  • Código backdooreado que supera las revisiones de publicación en npm
Comprueba tus conocimientos

Un pipeline verde en el escenario SCA garantiza que el proyecto no tiene vulnerabilidades. ¿Verdadero o falso?

Falso. Un pipeline verde confirma que no se detectaron vulnerabilidades conocidas con CVE en el rango auditado. Las vulnerabilidades zero-day y los paquetes maliciosos sin CVE registrado quedan fuera del alcance de npm audit.

Módulo 3 de 4 · Escenario 02

Secret Scanning: Token en Código Fuente

⏱ ~15 minutos 🔑 Control: Push Protection 🎯 GitHub PAT pattern — GH013
Al completar este escenario podrás:
  • Ver GitHub Push Protection rechazar un push con un secreto detectado
  • Explicar por qué el historial de Git hace crítica la acción preventiva
  • Aplicar la respuesta correcta: revocar antes de corregir
  • Reemplazar credenciales hardcodeadas con variables de entorno
Unidad 3.1

Contexto del problema

El archivo practice/scenarios/02-secret/config/settings.js contiene un token con el patrón github_pat_... que GitHub Secret Scanning reconoce como un Personal Access Token de GitHub.

⚠️
Importante — Token inválido El token incluido en este escenario es inválido y fue revocado inmediatamente. Su único propósito es demostrar la detección de patrones por Push Protection. Nunca lo uses como credencial real.
Unidad 3.2

Pasos del escenario

  1. Copia el archivo con el token a tu fork:

    mkdir -p config
cp practice/scenarios/02-secret/config/settings.js config/settings.js

  2. Intenta hacer push a una rama nueva:

    git checkout -b lab/secret-scanning-demo
git add config/settings.js
git commit -m "lab: agregar configuración con token (práctica Secret Scanning)"
git push origin lab/secret-scanning-demo

  3. Observa el bloqueo de Push Protection. La salida de Git será:

    remote: error: GH013: Repository rule violations found for
remote:        refs/heads/lab/secret-scanning-demo.
remote:
remote: - GITHUB PUSH PROTECTION
remote:   ——————————————————————————————————————
remote:   Resolve the following secrets before pushing again.
remote:
remote:   (?) GitHub Personal Access Token found in commit a3f9c12:
remote:       config/settings.js, line 15
remote:
remote:   To push, remove the secret from commit(s) or allow the secret:
remote:   https://github.com/.../security/secret-scanning/unblock-secret/...
remote:
 ! [remote rejected] lab/secret-scanning-demo -> lab/secret-scanning-demo
error: failed to push some refs

    El secreto nunca llegó al historial del repositorio.

  4. Entiende la respuesta correcta. Aunque el token de este escenario es inválido, en un caso real la acción más urgente es siempre:

    1. Revocar el token inmediatamente en GitHub → Settings → Developer settings → Personal access tokens
    2. Notificar al equipo de seguridad
    3. Luego limpiar el archivo

  5. Corrige el archivo reemplazando el token hardcodeado con una variable de entorno:

    const config = {
  apiUrl: 'https://api.example.com',
  // El token viene de una variable de entorno, no del código fuente
  token: process.env.API_TOKEN,
};
export default config;
    git add config/settings.js
git commit -m "fix: mover token a variable de entorno (eliminar hardcoded secret)"
git push

  6. Sin el patrón de token, Push Protection permite el push. En GitHub → Security → Secret scanning alerts verás la alerta marcada como auto-resuelta.

🏆
Código de verificación Cuando el push limpio llegue a la rama, el workflow publicará en el PR HSW-PRACTICE-02-XXXXXXXXXXXXXXXX.
Unidad 3.3

Conceptos clave

Por qué el historial de Git es permanente

Incluso si eliminas el archivo con el secreto en un commit posterior, el commit original permanece en el historial. Cualquier persona con acceso al repo puede recuperarlo con git log, git show <sha> o git reflog. Por eso Push Protection actúa antes del push: una vez que el secreto llega al historial, "eliminarlo" es mucho más complejo y puede requerir reescribir la historia.

Detección basada en patrones

GitHub Secret Scanning detecta más de 200 tipos de tokens de proveedores conocidos (AWS, Azure, Google Cloud, Slack, Stripe, GitHub, etc.) mediante expresiones regulares validadas contra sus formatos oficiales. Un secreto en formato personalizado o sin patrón registrado puede no ser detectado — razón por la que la revisión de código sigue siendo un control complementario necesario.

Comprueba tus conocimientos

Si Push Protection bloqueó el push, ¿necesito revocar el token igualmente?

Sí, siempre. Push Protection evita que el secreto llegue al repositorio, pero no sabes si fue expuesto de otra manera (logs locales, historial de bash, etc.). La revocación es la única forma de garantizar que el token no puede ser usado maliciosamente, independientemente de si el push fue bloqueado.

Módulo 4 de 4 · Escenario 03

SAST / CodeQL: DOM-based XSS con innerHTML

⏱ ~20 minutos (más 5–15 min de análisis CodeQL) 🛡️ Control: CodeQL js/xss 🎯 Taint tracking source → sink
Al completar este escenario podrás:
  • Interpretar una alerta de CodeQL con la cadena source → propagación → sink
  • Entender la diferencia entre análisis dinámico (tests) y análisis estático (SAST)
  • Aplicar el fix correcto: textContent en lugar de innerHTML
  • Resolver la alerta de Code Scanning en GitHub
Unidad 4.1

Contexto del problema

El archivo practice/scenarios/03-xss/src/demo-insecure.js usa innerHTML con el parámetro name directamente, sin sanitización. CodeQL ejecuta la query js/xss que traza:

  • Source: el parámetro name — datos de entrada no confiables
  • Propagación: el template literal incluye la fuente sin sanitización
  • Sink: outputElement.innerHTML = ... — interpreta HTML
⏳
Tiempo de análisis El primer análisis de CodeQL en un fork puede tardar entre 5 y 15 minutos. Si después de 20 minutos no hay resultado, cancela el run en Actions y vuelve a hacer push para reiniciarlo.
Unidad 4.2

Pasos del escenario

  1. Copia el archivo inseguro a tu fork:

    cp practice/scenarios/03-xss/src/demo-insecure.js src/demo-insecure.js

  2. Abre un Pull Request:

    git checkout -b lab/codeql-xss-demo
git add src/demo-insecure.js
git commit -m "lab: agregar ejemplo inseguro para práctica CodeQL (XSS)"
git push origin lab/codeql-xss-demo

    En GitHub, abre un Pull Request desde lab/codeql-xss-demo hacia main.

  3. Espera el análisis de CodeQL. En la pestaña Actions verás el workflow CodeQL Analysis ejecutándose. Cuando termine, el PR mostrará:

    • ❌ CodeQL / Analyze (javascript-typescript) — hallazgo HIGH detectado

  4. Revisa la alerta en GitHub → Security → Code scanning alerts. La alerta mostrará:

    Rule: js/xss  |  Severity: Error (High)
DOM text set from location-provided value

Source → name  (src/demo-insecure.js:4)
  ↓ taint flows through template literal
Sink   → outputElement.innerHTML  (src/demo-insecure.js:7)

    Si name fuera <img src=x onerror=alert(1)>, el navegador ejecutaría el handler de error.

  5. Aplica el fix. Edita src/demo-insecure.js:

    // ANTES (inseguro): HTML parseado — el navegador interpreta el contenido
outputElement.innerHTML = `<p>¡Hola, ${name}!</p>`;

// DESPUÉS (seguro): texto literal — el navegador no interpreta etiquetas
const p = document.createElement('p');
p.textContent = `¡Hola, ${name}!`;
outputElement.appendChild(p);
    git add src/demo-insecure.js
git commit -m "fix: reemplazar innerHTML con textContent para prevenir XSS (js/xss)"
git push

  6. Verifica que la alerta se resuelve. El nuevo análisis de CodeQL marcará la alerta como resuelta. El check del PR pasará a ✅ PASSED.

🏆
Código de verificación Con todos los checks en verde, el workflow publicará en el PR HSW-PRACTICE-03-XXXXXXXXXXXXXXXX.
Unidad 4.3

Conceptos clave

SAST vs pruebas automatizadas

Las pruebas automatizadas verifican comportamiento esperado — si la función devuelve el valor correcto para los inputs definidos en el test. CodeQL verifica propiedades de seguridad de flujos de datos — si datos de fuentes no confiables pueden llegar a sumideros peligrosos, independientemente de cuáles inputs se prueben. Es posible tener 100% de cobertura de tests y aun así tener vulnerabilidades que solo el análisis estático detecta.

textContent vs innerHTML

La diferencia es fundamental: textContent asigna texto literal — el navegador nunca parsea el contenido como HTML. innerHTML parsea el contenido como HTML, lo que significa que cualquier etiqueta o handler de evento incluido en el string se ejecuta en el contexto del documento.

Riesgo residual de SAST

SAST puede producir falsos positivos (alertas que no son vulnerabilidades reales) y falsos negativos (vulnerabilidades reales que no detecta). Los problemas de lógica de negocio, diseño inseguro y vulnerabilidades que requieren contexto semántico generalmente escapan al análisis estático.

Comprueba tus conocimientos

¿Por qué textContent protege contra DOM XSS pero innerHTML no?

textContent trata el contenido asignado como texto puro — el navegador lo renderiza como caracteres, sin interpretar etiquetas HTML ni ejecutar scripts. innerHTML parsea el contenido como HTML, por lo que un payload como <img onerror="robaCredenciales()"> se ejecuta en el contexto del documento con acceso a cookies y el DOM.
